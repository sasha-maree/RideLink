# 05 – Data Ownership

**Document type:** Data persistence boundary definition  
**Source of truth for:** Which service owns which data, IDs exchanged between services, and data isolation rules  
**Status:** Draft – Pending team review

---

## Critical Rule

> **One service must NEVER directly query or modify another service's database or tables.**
>
> If a service needs data owned by another service, it must obtain it through that service's API.
>
> This rule is absolute and has no exceptions.

---

## Data Isolation Principle

Each service has its own dedicated data store. The stores are logically and (ideally) physically separate.

| Service | Owns Its Own Database | May Query Other DBs |
|---|---|---|
| Account Service | ✅ Yes | ❌ Never |
| Driver & Vehicle Service | ✅ Yes | ❌ Never |
| Ride Management Service | ✅ Yes | ❌ Never |
| Fare & Payment Service | ✅ Yes | ❌ Never |

The database technology for all services is **MongoDB** (via Spring Data MongoDB). Each service must use a **separate database instance or separate logical database** to maintain isolation. No service may query another service's MongoDB database directly.

## Entity Ownership Map

### Account Service – Owned Entities

| Entity | Purpose | Key Fields |
|---|---|---|
| `accounts` | Core identity record | `account_id` (PK), `email` (unique), `password_hash`, `role`, `status`, `created_at`, `updated_at` |
| `profiles` | Personal information | `profile_id` (PK), `account_id` (FK→accounts), `first_name`, `last_name`, `phone_number`, `updated_at` |

> **Note:** The Account Service does NOT store driver-specific data (license, rating, vehicle). That belongs to the Driver & Vehicle Service.

---

### Driver & Vehicle Service – Owned Entities

| Entity | Purpose | Key Fields |
|---|---|---|
| `driver_profiles` | Driver-specific information | `driver_id` (PK = accountId from Account Service), `license_number` (unique), `rating`, `availability_status`, `created_at`, `updated_at` |
| `vehicles` | Registered vehicles | `vehicle_id` (PK), `driver_id` (FK→driver_profiles), `make`, `model`, `year`, `plate_number` (unique), `capacity`, `is_active`, `created_at` |

> **Note:** `driver_id` is not auto-generated by this service. It is the `accountId` issued by the Account Service, stored here as a reference. The Driver & Vehicle Service does NOT store the account's email, password, or profile. It only stores the `driver_id` as a foreign key reference.

---

### Ride Management Service – Owned Entities

| Entity | Purpose | Key Fields |
|---|---|---|
| `rides` | Core ride record | `ride_id` (PK), `passenger_id` (FK ref→Account Service), `driver_id` (FK ref→Account Service), `vehicle_id` (FK ref→Driver & Vehicle Service), `pickup_location`, `dropoff_location`, `status`, `distance_km`, `duration_minutes`, `requested_at`, `assigned_at`, `accepted_at`, `started_at`, `completed_at`, `cancelled_at` |
| `ride_status_history` | Audit log of status changes | `history_id` (PK), `ride_id` (FK→rides), `from_status`, `to_status`, `changed_at`, `changed_by` |

> **Note:** `passenger_id`, `driver_id`, and `vehicle_id` are foreign key **references** only. The Ride Management Service does NOT store passenger name, driver license, or vehicle make/model. It stores only the IDs. When it needs passenger details or driver details, it calls the appropriate service's API.

---

### Fare & Payment Service – Owned Entities

| Entity | Purpose | Key Fields |
|---|---|---|
| `fares` | Fare record for a completed ride | `fare_id` (PK), `ride_id` (unique, FK ref→Ride Management Service), `base_fare`, `distance_fare`, `surcharge`, `total_amount`, `currency`, `calculated_at` |
| `payments` | Simulated payment record | `payment_id` (PK), `ride_id` (FK ref→fares.ride_id), `fare_id` (FK→fares), `passenger_id` (FK ref→Account Service), `payment_method`, `status`, `processed_at` |
| `receipts` | Receipt record | `receipt_id` (PK), `ride_id` (unique), `fare_id` (FK→fares), `payment_id` (FK→payments), `issued_at` |

> **Note:** `ride_id` and `passenger_id` are foreign key references to other services. The Fare & Payment Service does NOT store ride locations, passenger names, or driver names. It reads that data from the Ride Management Service and Account Service at receipt generation time, then may cache a snapshot in the receipt for record-keeping purposes.

## Data That Must NOT Be Duplicated Unnecessarily

| Data | Owned By | Other Services Must NOT Store |
|---|---|---|
| Account email, password, name | Account Service | Duplicating profile data in other services is prohibited. Use the API. |
| Driver license number | Driver & Vehicle Service | Not to be stored in rides or fares. Reference by driverId only. |
| Vehicle make, model, plate | Driver & Vehicle Service | Not to be stored in rides. Reference by vehicleId only. |
| Pickup/dropoff locations | Ride Management Service | Not to be duplicated in fare records beyond what's needed for the receipt snapshot. |
| Fare amount calculation logic | Fare & Payment Service | Not to be replicated in Ride Management Service. |

> **Exception (Receipt):** The Fare & Payment Service may store a **snapshot** of the passenger name and driver name in the receipt record at the time of receipt generation. This is acceptable for receipt immutability (receipts should not change if an account name changes later). This is the only permitted form of data snapshot copying.

---

## Rules for Accessing Another Service's Data

| Rule | Description |
|---|---|
| R-01 | Always call the owning service's API. Never query the DB directly. |
| R-02 | Cache only if there is a clear performance or availability need, and the data is immutable (e.g., receipt snapshot). |
| R-03 | Do not store full copies of another service's entities in your own database. |
| R-04 | If a downstream service call fails, handle the error gracefully (see `07-communication-and-security.md`). |
| R-05 | Do not expose another service's internal data fields through your own API responses. |

## Database Technology Decision

**[RESOLVED]** – The team has decided:

1. All services will use **MongoDB**.
2. Each service will have its own separate MongoDB persistence boundary.
3. UUID is the confirmed identifier format across all services.

**[RESOLVED]** – The team has decided:
1. Naming conventions for documents and fields will use `camelCase`.

See OD-02, OD-10 in `01-system-overview.md`.
